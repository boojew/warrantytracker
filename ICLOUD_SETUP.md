# Private iCloud sync: setup and acceptance

## Current status

The code and separate development configurations are prepared. **No iCloud container has been registered or deployed, and real syncing has not been verified.** A free Personal Team cannot provision the required CloudKit capability. Apple lists paid Developer Program membership as a requirement for its [private database sync sample](https://github.com/apple/sample-cloudkit-privatedb-sync).

For now, run **WarrantyTracker-iOS** on your phone or **WarrantyTracker-macOS** on your Mac. Both use local storage. Settings → Storage & Sync reports **On this device**. Your free team can continue testing the local app. No subscription, membership purchase or account change has been performed by Codex.

## When a paid membership is available

1. Open `WarrantyTracker.xcodeproj`. In Xcode Settings → Accounts, add the Apple Account associated with the paid team. Keep the physical iPhone and Mac signed into the **same iCloud account**; this is separate from the developer team selected for signing.
2. Select **WarrantyTracker-iOS-iCloud** or **WarrantyTracker-macOS-iCloud**. Their Run actions select **Cloud Debug**. In Signing & Capabilities, select the paid team for that configuration on both app targets and enable automatic signing. Keep the normal Debug/Release configurations available for local testing.
3. Register the app identifier `com.boojew.warrantytracker` and the private CloudKit container `iCloud.com.boojew.warrantytracker` under that team, and associate the container with the app identifier. These names are planned identifiers, not proof of ownership or registration. If either is unavailable, resolve the identifiers before testing; do not casually change the bundle identifier of an installed inventory because that changes its app sandbox/data location.
4. For **Cloud Debug only**, verify the iCloud capability has **CloudKit** selected and the same container on both targets. Verify Push Notifications signing on both platforms. On iOS, verify Background Modes → **Remote notifications**. The checked-in entitlements and iOS plist already describe these capabilities. If Xcode changes them, review its changes so iCloud entitlements are not added to the free-team configurations.
5. Use the **Development** CloudKit environment. The supplied Cloud Debug entitlements select it. Check that provisioning profiles authorize the actual app identifier, container and notification entitlements. Unsigned builds prove compilation only; they cannot validate provisioning or sync.
6. Begin with disposable, synthetic inventory on test devices/accounts. Keep a separate backup of any valuable inventory before enabling sync on it. Install the cloud build over the local build using the same valid application identity; do not delete the installed app to fix signing, since deletion can remove its local inventory. Team changes and entitlement changes may require additional signing work.
7. On first cloud launch with an existing local database, the app makes a **Before-iCloud** snapshot alongside its store, including external attachment assets. If that copy fails, the app stops opening the inventory and shows an error; it does not silently start an empty store. The snapshot is made only once and is not a rolling backup. It has been tested by reopening it independently, but there is no user-facing Restore button yet. Do not manually replace a live SQLite file or its companion files.
8. Run both cloud schemes on the physical Mac and iPhone. Leave the apps open and connected for initial setup. In Settings → Storage & Sync, check account availability and any reported errors. **Check iCloud Status** refreshes the account status; it does not force a transfer. Apple schedules uploads, downloads and retries, so changes need not appear immediately. Completed upload/download times apply to individual operations in this app session, not proof that every device is current.
9. Verify development record types and operations in CloudKit Console. Follow Apple's schema-initialization guidance if development setup reports missing record types. Do not deploy the production schema or use these development-only schemes for App Store distribution in this milestone.

Apple's relevant guidance: [SwiftData sync setup](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices), [Core Data sync diagnostics](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer), and [development-to-production schema deployment](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema).

## Remaining acceptance checks — all pending on real devices

Use synthetic receipts and cards. Record both OS versions, app commits, signed configuration and observed results. The first synced MVP is accepted only after these checks pass:

- [ ] Enable cloud over an existing local inventory. The existing purchases, independent coverage records, card history, tags, defaults, main photos and multi-page PDFs remain, and appear on the other device. Verify dates and exact pre-tax amounts.
- [ ] Add purchases on each device before the first connection. Both inventories merge. Default categories, tags and locations appear once in pickers; existing links remain. Unrelated purchases are not combined merely because their names match.
- [ ] Change an item, coverage, card version, country/currency defaults and a catalog entry on each device. Confirm the other device receives each change, including after relaunch. A card update must retain purchase-time digits and links. A defaults change must not convert existing prices.
- [ ] Add an item photo, receipt, serial photo, five extras and a coverage PDF. Verify every byte/page is available on the other device, the main photo appears, and covered text stays covered. Test near the supported attachment limits and inspect quota/transfer failures.
- [ ] Make edits offline, quit/reopen offline, then reconnect. Confirm local persistence and eventual transfer both ways without manual re-entry.
- [ ] Edit different fields while both devices are offline, then reconnect. Also edit the same field differently. Record the framework's actual merge behavior and confirm both devices settle on the same result. There is no custom conflict-resolution screen or guarantee that both versions of a conflicting field are retained; this needs device validation before valuable data is trusted to sync.
- [ ] Delete an attachment, a coverage and an item on one device; confirm appropriate deletion on the other without deleting unrelated cards or lists. Check deletion versus an offline edit for resurrection or orphan records.
- [ ] Rename/archive the same default list entry on both devices, then reconnect. Confirm convergence, preserved item links and no repeated visible entries. Duplicate underlying list records are retained to protect relationships that may arrive in later imports.
- [ ] Check no network, unavailable iCloud, restricted access and quota failures. Status must explain the condition without claiming all data is synced. Saved changes must retry when possible. Test sign-out and account switching **only with disposable inventory** and record what happens to local/cloud data; their behavior is not yet verified or promised.
- [ ] Confirm the one-time pre-cloud snapshot remains readable and unchanged after later edits/deletions. Verify restore procedures separately before relying on it for recovery.

Do not reset the CloudKit environment, delete app containers, or switch production/development environments to troubleshoot an inventory containing valuable data. Continue using the local schemes until these checks are completed. OCR, AI extraction and share extensions are separate milestones.
